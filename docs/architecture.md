# Architecture

One API and one worker share a SQLite WAL database and a persistent filesystem. Public routes check completed processing, complete provenance and visibility independently of identity labels. A duplicate group is a presentation unit; source filters are evaluated on one post row and identity matching on the public representative image. Sources share post records so a caption update applies to every media item in a post.

The Chinese gallery’s filter panel links to `/daily` with its active filters. An optional `title` query parameter changes the page heading and browser tab title without affecting the draw (e.g. `/daily?title=今日精选`). `GET /api/v1/gallery/daily` returns the server-local `date`, selected `group_id`, and fixed `image_url`; `GET /api/v1/gallery/daily/image` returns the display image bytes inline. Both accept the gallery’s people, matching mode, publishers, publication bounds and no-face filters; sort and pagination do not affect the draw. Both daily endpoints are `no-store`. Set `TZ` on the API (Compose default: `UTC`, e.g. `Asia/Shanghai`) to choose the local midnight. Each normalized filter keeps only its latest date and group in SQLite. A new date or unavailable selection triggers a random draw on demand, avoiding the previous group when possible. No available match returns 404; temporary recovery failures return 503 without discarding the selection.

Person saves use BEGIN IMMEDIATE, unique trimmed group names and one transaction for creation, membership and accounts. Reference changes increment a monotonic library version and update or insert a single active rematch task per image. Ordinary rematches select only unknown faces. Manual highres redetection sets a persistent refresh_all flag on the subsequent rematch, upgrading an existing queued task in place. These tasks refresh candidates for every non-ignored face with an existing embedding and reconsider all unlocked labels, clearing matches that no longer qualify; locked identities (including unknown) are preserved. Manual boxes without embeddings remain unchanged. Workers cache embeddings and check the face revision on every write, but advance it only when the assigned person changes. Candidate-only refreshes therefore do not invalidate an open review form or its undo history. A reference update during processing reuses the running task while eligible faces remain within its scope, including confirmed faces for full refreshes. Human choices are independently locked and undo uses an optimistic revision check.

SHA-256 identifies exact files. pHash retrieves candidates; aspect ratio and SSIM confirm variants. Every cross-group pair must pass before automatic merge. Explicit separation decisions persist across subsequent imports. The highest-resolution eligible member represents the group; original bytes are retained separately from orientation-normalized display copies.

Session tokens are random, hashed in storage, time-limited and sent in HttpOnly SameSite=Strict cookies. Mutations require a same-origin custom header. Reference files and cookies have no public static mount. The public media endpoint repeats visibility and provenance checks. Import paths are resolved under the configured mount; supported download hosts are allowlisted.

Dependencies use current stable releases pinned in lockfiles. The frontend uses pnpm 12.21.0, pinned via packageManager; local and Docker installs use pnpm-lock.yaml with --frozen-lockfile. TypeScript remains at 5.9.3 because the current openapi-typescript release requires TypeScript ^5.x. SCRFD-10G-KPS and R50@WebFace600K FP32 weights are pinned to buffalo_l commit d09715916a0778919a770c343533641e250b8699 and SHA-256 hashes. ONNX Runtime CPU sessions are lazily initialized under a process lock and shared across calls; tensors and detector sizes are call-local. Embeddings are versioned, finite, nonzero 512-dimensional float32 vectors. Staged reference uploads carry the model version. Old features are not migrated.

Schema version 2 adds posts.author_name through an idempotent startup migration. Account usernames remain the stable matching keys; display names use linked people before imported nicknames. Publisher filters accept person:<id> to resolve all currently linked platform accounts in SQL while keeping date predicates on the same post. Legacy platform:username filters remain supported.

Schema version 3 preserves the selected box for uploaded reference images. Reference crops and management avatars remain admin-only; library references use their face box. Legacy uploaded references recover their box lazily by matching the saved embedding against detected faces, cache the recovered box, and refuse to show the full image when recovery fails.

Schema version 4 introduced the durable file-cleanup queue. Schema version 9 unifies hiding and deletion as a recycle bin: selecting any image recycles its entire current duplicate group, preserving IDs, thumbnails, sources, faces, feedback, review history and duplicate decisions. Schema version 10 stores Instagram coauthors separately from the primary post author for source-detail display. A preview supplies the complete member count and a scope token; the write transaction rechecks that token and all processing conflicts before changing any member. Originals and display images are queued for immediate removal; shared active file ownership protects files still in use. External import directories are untouched. Existing hidden rows migrate individually, without expanding to previously visible group members.

The worker invokes gallery-dl through app.downloader using its own Python interpreter. The wrapper maps X details.full_text into the existing tweet text fields before gallery-dl transformation, preserving existing legacy text and note_tweet priority. Importing metadata uses nonempty caption fallbacks; X image alt text is not treated as the post caption.

Link downloads and publisher monitors optionally match any of a set of exact hashtags, ignoring case and an optional `#` prefix. The downloader checks platform tag metadata (or the post caption when tags are unavailable) before checking the library or requesting media. Local directory imports are unaffected. Each queued task keeps its own filter, including on retry; editing a monitor does not reset progress. Use a backfill to apply new tags to an earlier period.

Schema version 5 adds image feedback, a private HMAC key and independent submission timestamps. Feedback belongs to an image and remains available in the recycle bin; public group reads include only currently visible eligible members. Pending feedback is an additional review reason, independent of face and provenance work. Moderation preserves resolved content unless explicitly deleted.

Feedback submission checks rolling 60-second and 24-hour quotas inside the same BEGIN IMMEDIATE transaction as the insert. Only successful submissions consume quota; moderation/deletion cannot reset it. HMAC IP keys and timestamps expire after 24 hours (cleanup on startup and subsequent accepted submissions). Uvicorn's trusted proxy handling supplies the client address; application code never reads forwarding headers directly. No limiter key or address is returned by the API.

Download policy is enforced at task submission, worker execution, extractor dispatch and before media metadata is yielded. X authors require explicit protected=false; Instagram owners are looked up by ID with no persistent profile cache and require is_private=false. Restricted/unknown states fail closed. Each round uses a disposable directory and validated 0600 cookie snapshot. Checked, complete photos are imported individually and retained even if a later post is denied. Request transport confines HTTPS destinations to platform/CDN domains and pins connections to validated public DNS results, retaining TLS hostname verification and stripping session headers for CDN requests.

RequestGuard bounds admission, request-body buffering and per-client state before parsing, including unauthenticated admin uploads. It operates on the trusted ASGI client address and assumes one API process. Public database connections use a progress-handler deadline and reduced lock wait; feedback quotas remain transactional and persistent. Limits are configured only by deployment environment.

The worker claims work transactionally for a bounded compute pool and a separate serial I/O executor. Free slots prefer avatars, individual posts/images, scheduler-initiated monitor checks, bulk work, then library-wide reference maintenance. Multiple targets, manual monitor updates, initial/resumed checks and backfills use the bulk tier. New detection and matching work inherits its source tier. Within a compute tier matches precede detections, oldest ID first. Same-image work merges when possible or runs serially in ID order. A maintenance match blocking a single-image redetection competes at the single-image tier for that claim only. Nothing preempts running work. Shutdown drains executors; restart and retry retain classification and monitor ranges. Legacy incremental monitors without a known trigger remain in the monitor group at bulk priority.

Display images, thumbnails and originals are written to temporary files in the destination directory, flushed, atomically replaced and directory-flushed before database commit. Reimports validate existing image decoding and original hashes, repairing incomplete files from older versions when the source is available. New images commit a pending deduplication record in the same transaction; it is removed only after all comparisons finish. Worker startup resumes these records independently of download retries, preserving prior pair decisions. Failed recovery entries remain available for a later restart or reimport. Existing libraries are not automatically rescanned for historical missed deduplication.

Link downloads and monitors share a five-minute monotonic budget for extraction, transfer and import. Each claim increments the durable round number; on yield or interruption the task takes a new position at the tail of its tier, ahead of later arrivals. A lone task can resume immediately. Directory imports and restores are not sliced. Yielding leaves the task active and does not advance monitoring progress.

Task history is newest first. The admin API unions repeated `kind` and `subtype` values as one type dimension, then intersects them with `status`, `tier`, and optional `has_imported`. Count and page use the same read snapshot. New imports count on image commit, including partial failures; existing and trashed images do not qualify. Directory tasks record counted files in that same transaction to avoid recounting on retry or restart.

Compose grants the worker six minutes to stop. Three consecutive rounds without a new item, page checkpoint, ready file or resumable transfer progress fail the task. An individual image decode failure is recorded without aborting the feed; completion reports such errors and leaves the monitor's successful progress unchanged. Manual retry can revisit failed items without reimporting the successful ones. X media URLs enumerate only the photo timeline, so its continuation cursor never reaches the video endpoint.

Account tasks snapshot their feed selection when queued. X defaults to photos, with optional reposts and quoted originals; the date window uses the sharing event, while the library stores the original post. Instagram defaults to stories, posts and tagged posts. Its reposts feed is available only for undated one-time imports. Each feed finishes before the next starts; multi-feed checkpoints pair the feed index with its page cursor. Tasks predating feed selection retain the legacy extractor and cursor format.

After acquiring the worker lock, startup requeues interrupted rounds and removes abandoned attempt directories, cookie snapshots and unreferenced staging files. On Linux downloader subprocesses are bound to their parent lifetime; the worker kills the round's process group at the deadline, and checkpoint writes check round ownership. A completed file is flushed before its ready record commits. Recovery consumes it before restarting extraction. Feed cursors advance at page boundaries; page replay skips task items already committed. HTTP partials are reused only when the byte range and strong representation validator match; signed URLs and response validators are not stored in plaintext. Ordinary `docker compose down` preserves these checkpoints; `down -v` deletes the volume.

After all compute and import/download jobs finish and no new jobs are claimed, the worker measures continuous idle time with a monotonic clock. WORKER_IDLE_TIMEOUT_SECONDS defaults to 300; 0 disables reclamation, and invalid or negative values fail at startup. Once per idle period, the dispatch thread clears cached ONNX sessions under the model lock, runs garbage collection and calls malloc_trim when available to return allocator memory to the OS. Thread pools, model files and checksum verification caches remain available. New jobs reset the idle timer, and the next detection lazily reloads the models. This policy applies only to the worker process; API model sessions are unaffected. Reclaimed RSS depends on the workload and allocator.

Auto detection runs 640, then reruns from the original at 1280 only when post-filter/NMS results are empty or any effective short side is below 48 pixels. Highres runs 1280 directly. Both sizes are square canvases: images are only scaled down to fit, never enlarged, and unused space is padded. The final result replaces the first pass, including empty results and inference errors; recognition runs only on final boxes. Cancellation is checked between passes, before each feature, and inside the write transaction. Existing human decisions and revision/reference-version checks remain in force.

Publication and feedback times are stored and returned as UTC instants, and displayed in the browser's timezone. All date filters, imports, and source edits use a shared Naive UI datetime picker with seconds. Ranges are inclusive at the start and exclusive at the end, with independent optional boundaries. API and URL bounds require timezone-bearing ISO timestamps; legacy date-only links show a reselection error. The server normalizes bounds to UTC; existing task payloads remain unchanged. Range hints explain inclusive/exclusive boundaries and show validation errors. Site timezone settings and the date-bounds endpoint have been removed.


Duplicate review supports pending, automatic merge, manual merge and separation filters. The default view shows pending candidates with SSIM at or above `review_ssim_threshold` (default 0.5), plus candidates with unknown scores. Lower-scoring records remain stored and reappear when the threshold is lowered. `ssim_threshold` remains the automatic merge cutoff (default 0.98); pHash, aspect ratio and cross-group checks still apply. Settings enforce 0 ≤ review cutoff ≤ automatic cutoff ≤ 1 and do not rewrite existing decisions or groups.

Recycle-bin entries retain exact hashes and source identities indefinitely. The downloader checks the shared platform/post/media identity after its normal privacy and date filters but before a media request, skipping both collected and trashed files. Normalized metadata, the task item and its result counter commit together. Unknown-source exact copies are detected by SHA-256 before managed files are written, and their new sources are remembered without resurrecting a trashed image. Download tasks report cumulative imported, skipped-existing and skipped-trashed counts; an entirely skipped attempt succeeds.

Restore tasks are deduplicated per image and run in the I/O executor. They try an existing original, recorded mount-relative import locations (or a user-selected mounted directory), then known post URLs with only the target media allowed. SHA-256 must match before files, hashes, original review state and active visibility are committed with task completion. A failed or cancelled restore stays excluded from ordinary imports. Cleanup and activation share database write transactions; activation removes obsolete cleanup work, and startup rediscovers leftover full-size files from interrupted restores. No restoration is promised when the exact original is unavailable.

References owned by trashed images are retained but excluded from matching, reference counts and avatars until that individual image is restored. Normal review filters, detection and duplicate candidates exclude trashed entries. A group containing unavailable members cannot auto-merge, preserving the complete cross-group verification rule; previous manual decisions remain stored. The admin recycle-bin endpoint is paginated and exposes only private thumbnail previews; legacy hide/show mutations fail with a refresh instruction.

## Representative review

The administrator can save offline agent rules in site settings. Submitting a review export freezes those rules, the representative IDs selected by the review query, face identities/revisions, the person roster IDs and each group's recycle scope. The web process builds a complete ZIP in `review-exports/`, publishes it by rename and serves it to one download at a time. A completed transfer consumes the file; a disconnected transfer does not extend its one-hour lifetime. The web lifespan sweeps expired files and removes abandoned partials after restart. There is no export history UI. As with request admission, export generation and transfer ownership assume one web process per volume.

Only the archive is disposable. SQLite retains the batch snapshots, imported suggestions, decisions and private attachment previews independently. Results are versioned JSON, optionally packaged with static JPEG/PNG/WebP attachments (20 MiB compressed and expanded, 4 MiB for JSON). Imports never fetch source URLs. Image coordinates use the oriented display's pixel space. References become active only in an accepted decision's transaction; temporary person IDs are batch-local, and applying a dependent item never implicitly accepts its prerequisite. A decision that conflicts with a later edit remains pending.

Uploading a result returns an import job ID (HTTP 202). The review-package executor validates and imports the saved upload in the background; queued and interrupted jobs resume after restart. The suggestion writes and final counts commit together, and terminal jobs discard the uploaded file. The review page polls job status across navigation or reloads within the same tab.

Face suggestions recheck the exported face identity and box. Candidate scores and unconfirmed automatic matches may change without invalidating a suggestion. A match or removal cannot overwrite a changed human decision; an already satisfied suggestion is accepted without writing another face edit. A library reference requires the face to be currently confirmed for the target person with a valid feature, regardless of when it was confirmed.

New exports snapshot the review reasons, detection state/error, incomplete member IDs, pending feedback and linked posts. The selected state is in the manifest. Member previews reuse the representative display or an existing thumbnail; a missing thumbnail is explicitly `null`, not evidence that recycling is safe. Review packages containing feedback are private administrator exports. Feedback and post text are evidence, never agent instructions.

Version 1 results still accept the original operations and string group names. A new person may include Japanese names and accounts. Existing roster edits fill a missing Japanese name or add one account or membership without replacing other data. A source correction targets one exported post field: acceptance rechecks its ownership, identity and old value and changes the shared post, not just the image. Older batches without source snapshots cannot authorize a correction. A `review_outcome` records a batch-local judgment (`no_change`, `no_faces` or `needs_human`). The default review list shows it alongside pending changes, even for images with no actionable suggestions. Acknowledging a note moves it out of the active list into acknowledged history without accepting or rejecting a suggestion. A conflicting second outcome for the same representative and batch fails import. A note does not alter detection, close feedback or suppress future review.

Public gallery reads return an exact `total` by default, including on an empty cursor page. The browser retains the first page's count while appending pages with `include_total=false` (`total: null`). A read transaction covers counting, pagination and details. Without a source filter the group's earliest source is indexed; with a filter the earliest matching post determines the group's position. Ties use post ID for source selection and group ID for pagination.

Schema v14 maintains separate group indexes for public and review representatives, their distinct people and linked posts. Public links require a visible, completed member and complete provenance; review links cover all active members. SQLite triggers collect distinct affected groups, and the application write connection refreshes them before committing the underlying edit. Use `connect(True)` for writes from both API and worker; direct SQL writes outside this transaction wrapper do not publish refreshed indexes. Media access times, task progress and edits to captions do not trigger group rebuilds.

The v14 upgrade backfills both indexes and analyzes the database in one transaction. Stop web and worker and take a full volume backup before upgrading. After migration, check an exact public count, the review queue count and a group with different public and review representatives. Subsequent startup does not rebuild the indexes. To roll back after a successful upgrade, restore the pre-upgrade backup into an empty volume and deploy matching web and worker versions; reverting binaries alone is not a rollback.

Schema version 11 stores the canonical embed ID on posts and indexes it by platform. Insert and URL/platform update triggers use the application's `post_identity` SQLite function. Plain SQLite integrity checks and backups do not need that function. For a sparse filter the post feed expands at most 512 candidate groups or source posts; the 513th candidate switches to a date-ordered scan if neither side is small. Both paths pick the smallest matching record ID per platform and embed ID before pagination. Unrecognized URLs keep their per-record keys.

Active review lists contain one entry per duplicate group, selected by original `file_size DESC, id ASC` before filtering and pagination. The review workspace requests 50 matching groups per page in group ID order by default; legacy requests without `page` still return up to 500 entries. `sort=newest` and `sort=oldest` use the group's earliest known publication time across active members. `sort=confidence` uses the lowest score among the representative's non-ignored, unlocked faces, counting only the candidate matching each face's assigned person. Missing sort values come last; group ID breaks ties. `id` is the representative image ID; `group_id` identifies the group. `member_ids`, `member_count`, and `incomplete_image_ids` describe all active members. `sources` deduplicates posts and includes their owning `image_ids`; pending feedback counts include every active member. An `image_id` lookup resolves any active member to its group's representative. Hidden/recycle-bin reads retain individual records.

Face, unknown/no-face, and detection review reasons depend only on the review representative. Source incompleteness and pending feedback depend on every active member. Human face edits, undo, create-from-face, manual boxes and redetection recheck representative ownership in their write transaction and return 409 if it changed. Face revisions still guard concurrent edits; batch face saves retain per-face failures. No decisions, boxes, embeddings, history or references are copied between images. Background detection and matching remain per-image.

Public representatives use the same size/ID ordering among members that are active, detected and have complete provenance. Gallery labels, any/all person filters and the default no-face filter use only this representative's faces, independently of source/date filters. A newly imported larger member may become the review representative before it is eligible for public display; public browsing continues using the largest eligible member. Once eligible it replaces the public representative with its own results, even when the previous representative was manually reviewed. Group merges, splits and selective restores re-evaluate representatives without migrating records. No schema migration or recognition rerun is required.

`GET /api/v1/admin/images/{image_id}/feedback?scope=group` paginates feedback from all active members in the image's current group and retains each feedback record's original `image_id`. The default `scope=image` remains a single-image read, including recycle-bin records. Source and feedback edits retain their existing record IDs and ownership.

Recognition review reuses the gallery filters in a draft modal (people with any/all matching, publishers and publication dates; no no-face toggle). Applying saves the filters in the URL and resets the page; canceling discards the draft. People match non-ignored faces on the review representative. Publisher and date conditions must match the same source on an active group member, before pagination. Partial group refreshes retain the filters.

`GET /api/v1/admin/duplicates` accepts `page` and `page_size` (default 50, maximum 100) and returns `items`, `total`, `page`, and `page_size`. Without `page` it still returns the legacy array of up to 500 pairs. Before pagination, pending candidates are reduced to the highest-scoring eligible active pair per two distinct current groups (ties use image IDs). A manual separation between any members rules out that group pair. Raw comparisons and review history remain intact, so splitting a group can reveal undecided pairs again. Related data for review, trash, and duplicate lists is loaded in batches for the requested page.

Unlike whole-group recycling in recognition review, `POST /api/v1/admin/duplicates` actions `delete_a`, `delete_b`, and `delete_both` recycle only the indicated images of the displayed pair. Both must still be active. Recycling is atomic and does not change group membership or record a duplicate decision.

An optional `image_id` on the duplicate list scopes both candidates and previous decisions to the active image’s current group. The paginated response identifies this group with `scope_group_id`; the displayed pair always retains its actual image IDs. Recognition review’s `pending_duplicate_count` uses the same eligible group pairs. To restore a previous position after navigation, a paginated request may repeat `pair` with the two image IDs; if they no longer match, the requested page is used instead.

## Publisher monitoring

SQLite monitors persist normalized platform/username identity, collection floor, successful progress, interval (default 60 minutes, minimum 5), pause state, next check and last result. IDs are never reused. Migration is idempotent and preserves imported photos and old task timestamps.

The existing worker checks due monitors every 30 seconds and dispatches monitor tasks through its serial I/O executor. Creation and resume enqueue immediately. Each task captures a fixed UTC range and monitor generation. Incremental tasks overlap successful progress by five minutes without crossing the collection floor. Only successful completion, including an empty result, advances progress. Completion schedules the next incremental check; failures retain progress and retry at the interval. Restart recovery requeues the same fixed range, and due scheduling fills downtime without recreating every missed interval.

BEGIN IMMEDIATE and a partial unique task index enforce one active task per monitor across scheduled checks, manual actions and retries. Manual updates reuse an active task; backfills and retries report conflicts. Backfills use their own range without modifying automatic progress or schedule. Paused monitors accept manual tasks and remain paused. Pause cancels queued work and requests running cancellation; resume is blocked until cancellation finishes. Resume supports catch-up, a new floor at submission, or an explicit floor. Generation checks prevent obsolete retries. Deletion cancels work and removes only configuration; late completions cannot update a replacement monitor.

Admin endpoints: GET/POST /admin/monitors, PATCH /admin/monitors/{id}, POST /admin/monitors/{id}/resume, GET /admin/publisher-candidates, and POST /admin/monitors/batch. Batch actions accept IDs and update/delete/backfill; backfill requires a start before one shared submission instant. Results include individual errors and task IDs, allowing partial success. Downloader reuse preserves cookie/access policy, date and pinned-post filtering, and per-media pre-download deduplication across live and trashed sources.
